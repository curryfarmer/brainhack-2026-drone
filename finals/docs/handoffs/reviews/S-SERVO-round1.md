## Findings

finals/tests/test_servo.py:203: MED TEST: every pixel_offset_to_move test passes k=1.0, so the gain constant k is never exercised at a non-unit value. Mutants that NEUTRALIZE the camera gain survive the whole suite: dropping `k *` from line 193 (step = |error_norm*altitude_m*100|), or `k * error_norm` -> `error_norm / k`, both give identical output at k=1.0 (verified: k=1 step 25 cm == the only-pinned value; k=2 should be 50 but no test checks). k is the onsite-calibrated lateral gain (gate F) — a silent neutralization mis-tunes every centering Move. Add a test with k=2.0 (and/or k=0.5) at a fixed offset asserting step scales linearly with k vs the k=1.0 baseline.

finals/mission/phases/_servo.py:185: LOW BUG: only bbox_xyxy[0] and [2] are finiteness-checked; bbox[1]/[3] (y0,y1) pass NaN/inf silently (verified: bbox=(300,nan,340,inf) returns a Move, no raise). Harmless to THIS function (it uses only x0/x2), but the docstring/validation surface implies the bbox is validated and a future helper reusing the same bbox could inherit the unchecked NaN. Either loop over (0,1,2,3) or document that y is intentionally unused. (Note: test_servo.py:322 only pins bbox[0] NaN -> a mutant that drops the [2] check while keeping [0] would survive; widen test_pixel_move_rejects_nonfinite_bbox to also feed NaN at index 2.)

finals/docs/module_map.md:123: MED TEST: the recorded NAV-3 kill-check rationale "wrap180 >= boundary was equivalent -> proved dead-code & removed" is FACTUALLY WRONG. `>=` maps wrapped==180.0 to -180.0 (verified for 180/-180/540), violating the closed-+180 contract; the `> 180.0` in the code is load-bearing, not arbitrary, and the existing tests DO kill the `>=` mutant. finals/tests/test_servo.py:262: LOW TEST: the m->cm `* 100.0` (line 193) and `/ frame_w` normalization (line 192) are pinned only transitively via the single low==25/high==50 assertion at k=1,alt=1/2,px+160. finals/mission/phases/_servo.py:135: LOW OPT: hot path (called from land_on_pad/navigate step() ~10 Hz). `bearing_error_to_rotate` calls clamp(error, -max_step_deg, max_step_deg), which re-runs `_require_finite` on error, -max_step_deg, and max_step_deg every tick — error is already finite (wrap180 output) and the two step bounds were validated at function entry (lines 122/127). 3 redundant isinstance/isfinite checks per tick. Impact: negligible (microseconds; arena is tiny). REJECT a fix that inlines a bare min/max here — it would DROP the lo<=hi fail-loud guard and obscure the clamp semantics. Correctness > clarity > perf; leave as-is or, if ever hot enough to matter, add a private `_clamp_trusted` that skips re-validation ONLY for already-validated callers (not worth it now). SCALING note only.

finals/mission/phases/_servo.py:193: LOW OPT: hot path. `pixel_offset_to_move` recomputes `clamp(abs(k*error_norm*altitude_m*100.0), min_cm, max_cm)` which re-validates min_cm/max_cm (already validated at lines 169-180) every tick. Same disposition as above: negligible, and removing the clamp's internal guard would drop a fail-loud check — REJECT. No per-call list/dict/tuple allocation exists in either helper (Move/Rotate are the only allocations and are the required return value). No recomputable module constant. Nothing to fix.

finals/mission/phases/_servo.py:195: LOW BUG: `int(round(step_cm))` uses Python banker's rounding (round-half-to-even): round(0.5)=0, round(2.5)=2. A sub-cm step at exactly x.5 rounds to even, not up. Only matters at the min_cm clamp floor or near-zero raw steps; with min_cm>=1 (configs) and the clamp this is benign, but it means a 0.5 cm raw step rounds to 0 cm -> Move(distance_cm=0) is POSSIBLE only if min_cm==0 (test_servo.py:285 uses min_cm=4 so never hits 0). No test pins a half-cm input; not exploitable under the shipped configs (min_cm>=1). Documenting for completeness; no action required unless a config sets min_cm=0 (then a 0 cm Move could be emitted — land_on_pad/navigate should reject 0 cm, verify in those slices).
